大模型的上下文（Context）

LLMcontext-windowattentioncontext-engineering
生成日期：2026-09-12 · 视角：AI Agent 工程 / 自我学习者 · 格式：HTML
一句话定义：大模型的"上下文（Context）"是一次推理中模型能看见、并据以生成下一段文本的全部输入——包括系统提示、对话历史、工具定义与返回、附加文件与 Skill 等所有 token。它的总长度受 context window 限制，且它是"短期舞台"，不是"长期记忆"。[来源 1][来源 2]
假设标注：本资料假设读者已调用过 LLM API，见过 system / user 这类消息角色，但未系统了解上下文管理。默认视角为 AI Agent 工程。

1 · 学习目标

学完这份资料后，你应该能够：

  1. 准确说出"上下文"包含哪些东西，并把它与"对话历史"、"提示词"这两个常被混用的词区分开。
  2. 解释为什么"上下文窗口越大 ≠ 模型记得越准"，并说出至少两种工程上的应对手段。
  3. 在一个真实任务里估算输入 token 的主要构成，并指出哪部分可以精简。

2 · 核心问题

  1. 上下文里到底装了哪些东西？为什么说"提示词只是上下文的一部分"？
  2. 为什么扩大窗口不能解决"模型记不住中间内容"的问题？
  3. 上下文工程（context engineering）和提示工程（prompt engineering）的区别是什么？
  4. 在长任务中，应该"压缩"还是"重开一个新窗口"？判断依据是什么？

3 · 个人解释

🔍 本板块含个人理解，标注为「待人工复核」的部分建议用自己的话再改写一遍。

我理解上下文最有效的一个类比是"没有记忆的演员 + 有限的舞台"。

把 LLM 想象成一个演技很好但没有记忆的演员。每次演出开始、灯光亮起的那一刻，导演必须递给他一沓纸——这沓纸就是 context window。纸的容量是有限的，纸上写了什么，他就只能演出什么。演完谢幕，他完全不记得上一场演过什么。

这个类比帮我解开了很多"AI 好像变笨了"的困惑：模型"忘了前面说过的要求"，不是它不听话，而是那段内容已经被挤出了这沓纸；模型"前后自相矛盾"，也不是它"学坏了"，而是纸上内容太多，中段细节没被注意到。

我一开始把"上下文"理解成一个能存东西的地方，后来才明白它更像个动词：它描述的是"这一次推理，模型能看见什么"这个边界。这个边界不是固定的，是被调用方一次次重新拼出来的。所以我现在的判断标准是：凡是"记不住"的问题，先别怪模型，先去看那沓纸上写了什么、写在第几页。

4 · 核心机制 / 组成

  • 按 token 计，不按字符或词计。token 是模型的最小感知单位；同样的内容，中文与英文的 token 数并不相同。[来源 3]
  • 有一个硬上界。窗口满了请求就会失败——所以目标不是"把一切都塞进去"，而是"把对的东西塞进去"。[来源 2]
  • 输入与输出都要计费。上下文越长，单次调用越贵、越慢。这是"整理上下文"最直接的经济动机。[来源 2]
  • 注意力随距离稀释。窗口变大时，模型对中段内容的准确引用能力会下降，这一现象被称为 "lost in the middle"，且被实验系统量化过。[来源 4]
  • "上下文腐烂"是渐进的。随着 token 数增长，模型准确回忆信息的能力单调下降，所有模型都受影响，只是下降斜率不同——因此是精心策划上下文，而非单纯扩大窗口。[来源 1]
  • 可被显式工程化。压缩摘要、即时检索（just-in-time）、结构化笔记、子 Agent 架构、提示缓存，都是上下文工程的具体手段。[来源 1][来源 2]

6 · 应用场景

谁：一位需要读长篇报告的从业者。
什么环节：让模型基于一份 80 页的 PDF 回答一个具体问题。
解决什么问题：直接整篇塞进去，模型经常漏掉中段内容，回答不完整。

可行的做法是先做"层级摘要"：把 PDF 切块，每块先让模型抽出简短章节摘要，再把所有摘要合起来去回答问题。

# 伪代码：层级摘要
chunks = split_pdf(pdf, by='page', chunk_size=1000)   # 约 35 块
summaries = []
for c in chunks:
    s = llm.complete(
        system="用 200 字总结这一段的关键词和结论",
        user=c
    )
    summaries.append(s)

# 用信息密度更高的摘要回答原问题
final_answer = llm.complete(
    system="基于以下章节摘要回答问题。",
    user=f"问题：{question}\n\n章节摘要：\n" + "\n\n".join(summaries)
)

塞进上下文的 token 变少了，回答质量却可能更好——因为模型看到的是精炼版，而不是一叠噪音。这正是上下文工程的核心主张：决定质量的是窗口里装了什么，不是窗口有多大。[来源 1]

7 · 易混淆 / 使用边界

常见误解正解
上下文窗口大 = 模型能精确用满所有空间 长上下文中模型对中段细节的引用能力显著下降（"lost in the middle"），且"上下文腐烂"是随 token 数增长的渐进衰减。[来源 4][来源 1]
清空对话 = 模型"失忆了" 清空的只是当前会话的上下文；跨会话的"记忆"要靠额外的存储机制设计，不是窗口自带的。[来源 2]
提示词（prompt）就是上下文 提示词是上下文的一部分。上下文还包括对话历史、工具定义与返回、附加文件、Skill 元数据等所有 token。[来源 2]
长上下文可以替代 RAG 两者解决不同问题：RAG 负责"找得到"，长上下文负责"装得下"。生产中常常配合使用——先召回少量高相关片段，再让模型基于它们作答。

不适用 / 会失效的情形：

  • 需要跨会话长期记住的偏好与决策 —— 上下文默认不保留，需借助外部存储或记忆机制。
  • 对成本与延迟极度敏感的批处理 —— 无节制地堆上下文会直接放大账单和响应时间。
  • 需要精确引用长文档中段内容的任务 —— 仅靠"窗口够大"不可靠，应配合检索或分块摘要。
  • 把上下文当作安全边界 —— 上下文里的内容不等于"可信指令"，来自工具返回或外部文档的文本可能包含注入内容，需要额外防护。

8 · 自测问题

先自己作答，再展开答案对照。

简答题

  1. 【概念辨析】"上下文"、"提示词"、"对话历史"这三个词的关系是什么？
    查看答题要点

    要点：上下文是最大的集合，指一次推理中模型能看见的全部 token；提示词（system prompt / 用户提示）和对话历史都是上下文的子集。除此之外，上下文还包含工具定义与返回、附加文件、Skill 元数据等。常见错误是反过来把上下文当成提示词的一部分。[来源 2]

  2. 【核心机制】为什么单纯扩大上下文窗口，无法解决"模型记不住中间内容"的问题？
    查看答题要点

    要点：因为限制不只是"装得下"，还有"能不能被准确注意到"。实验显示模型对长上下文中段信息的引用准确度明显低于开头与结尾（lost in the middle）；同时随着 token 增长，回忆能力呈单调下降（上下文腐烂）。窗口变大反而可能让更多低信号内容挤占注意力。所以正解是提高上下文的信噪比，而不是无限扩容。[来源 4][来源 1]

选择题

  1. 【风险与边界】以下哪种做法最不能缓解"上下文过长导致回答质量下降"？
    A. 对历史对话做摘要压缩
    B. 用即时检索的方式按需拉取资料，而不是预加载全部
    C. 把上下文窗口换成更大的模型
    D. 把关键约束反复放在系统提示的开头
    查看答案与理由

    正确答案：C
    理由：换成更大窗口只是延后触顶时间，并不改变"注意力被稀释""中段引用准确度下降"这些机制性问题，还可能因为装入更多低信号内容而恶化信噪比。A、B、D 都是直接作用于"上下文里装什么、放在哪"的手段，属于上下文工程的正解。[来源 1][来源 2]

应用题

  1. 【具体应用】设想你要让模型基于公司内部 20 份文档回答一个问题。请设计你的上下文组织方案，并说明为什么这样组织。
    查看答题要点

    要点：合理方案应体现至少两点：① 先用检索（RAG）筛出高相关片段而不是全量塞入；② 把最关键的约束放在开头或结尾以规避中段衰减；③ 对超长文档先做分块摘要再拼接；④ 保留本轮问题在靠后位置。评分重点在于"是否解释了信噪比与位置这两个考虑"，而非方案是否唯一。

  2. 【风险与边界】什么情况下你应该选择"重开一个新窗口"而不是"继续压缩当前上下文"？
    查看答题要点

    要点：当压缩会损失继续推进所必需的状态时（例如任务早期写下的测试清单、约定、关键决策），而模型又能从文件系统或结构化笔记中重新发现这些状态时，重开新窗口往往比反复压缩更干净——它避免了摘要误差的层层累积。反之，若任务连贯依赖大量隐含上下文而不可能从外部恢复，则更适合压缩续跑。答出"状态能否从外部重建"这个判断依据即为合格。
