三个概念之间的关系

mappingagent-loopcontextskill
生成日期：2026-09-12 · 关系说明 · 格式：HTML（同内容另见 concept-relationship.md）
这三个概念不在同一层：大模型的上下文是 Agent 的"短期舞台"；Agent 是在这个舞台上跑循环的程序；Skill 是教会这个程序"按什么流程工作"的手册。下面把它们的边界、相互影响与协作方式讲清楚。

2 · 上下文如何影响 Agent 的工作

Agent 的决策质量几乎完全被两件事决定：决策点（由 LLM 完成）和上下文里装了什么。因为 LLM 在做每一个决策时，能看见的只有上下文窗口里的 token——上下文就是 Agent 的短期认知上限。这条影响可以从三个层面看：

2.1 三个层面的具体影响

影响维度具体机制失效时的表现
信息完备度
（装得下吗）		 窗口决定能同时容纳多少对话历史、工具返回与文档片段。装不下就要裁剪，裁剪就意味着丢失。 忘记早期约定；重复做已经做过的事；用户不得不反复重申要求。[来源 2]
行为约束
（被什么约束）		 系统提示中的角色、边界、工具使用偏好构成上下文里的"宪法"，最先影响决策风格。 该收敛时不收敛（跑太多轮）；该调用某个工具时不用；越出手册规定的范围。[来源 1]
信噪比与位置
（注意得到吗）		 上下文越长，模型对中段信息的引用能力越低（lost in the middle）；关键信息放开头/结尾更可靠。 前后自相矛盾；引用了已经不相关的旧信息；忽略了放在中间的硬约束。[来源 3]

2.2 一个具体例子：同一个任务，三种上下文

任务固定为"调研最近 30 天最热的 5 个 AI Agent 仓库"，只改变上下文内容：

上下文配置典型结果
只有用户原话，无系统提示Agent 自由发挥，可能反复搜索，输出冗长且重点分散
系统提示规定"最多 3 次工具调用，输出不超过 200 字"行为明显收敛，输出精炼，但深度有限
系统提示 + 检索策略类 Skill 被触发加载Agent 走专业化路径：先筛后读再抽取，质量与结构同时提升

三次的差别只来自上下文——模型权重、工具集、循环结构都没变。这就是"上下文决定 Agent 上限"最直接的证据。

2.3 反过来：Agent 也在塑造自己的上下文

影响是双向的。Agent 每跑一轮都会产生新的工具返回，如果不加管理，上下文就会单调膨胀直至触顶（参见 llm-context.html 图 2）。所以成熟的 Agent 必须主动整理自己的上下文：压缩历史、把状态写入文件、丢弃低价值的中间结果——这本身就是"上下文工程"在 Agent 场景下的落地。[来源 2]

3 · Skill 如何沉淀可复用的任务知识

如果说系统提示是"宪法"，那 Skill 就是"手册"——它把某一类任务的经验固定下来，下次遇到相似任务可以再次调用。区别在于：宪法每次都在，手册要用时才翻。

3.1 任务知识的四个沉淀层次

层次存放位置谁来维护复用范围是否常驻上下文
本次会话对话历史用户 + Agent仅当前任务是（逐轮累积）
System Prompt每次请求注入开发者手写该应用的全部任务是（始终）
Skill.workbuddy/skills/<name>/SKILL.md编写者 / Agent 协助所有 description 匹配的任务元数据常驻，正文按需
外部知识库向量库 / 文档系统检索服务运行时按需召回否（召回片段才进）

Skill 的位置很特殊：它兼有 System Prompt 的"自动触发"和知识库的"结构化内容"。正因如此，它特别适合沉淀三类知识：

  1. 重复性工作流——"每次都要按这套步骤做"的活儿，写一次，之后一句话触发。
  2. 领域规范——团队约定、领域偏好，让 Agent 不必每次被重新交代。
  3. 专家经验——把"老手才会注意的坑"变成可执行的检查项。

3.2 沉淀的完整链路

图 2 · Skill 从沉淀到复用的生命周期
① 沉淀                ② 加载                 ③ 复用                 ④ 迭代
写 SKILL.md    ──▶   元数据语义匹配   ──▶   按流程执行任务   ──▶   根据反馈修订
（YAML + 正文）       命中则加载正文         产出落到约定位置        （修订回写文件）
      │                     │                      │                     │
      │                     │                      │                     └─▶ 回到 ①（版本更新）
      │                     └─ 未命中则不加载：不占用上下文
      └─ 一次投入

收益：写一次 → 任意会话可用 → 团队共享 → 改一处，全部场景同步生效
代价：description 写不准会导致触发失败；写得过宽会导致误触发

图说：Skill 的价值来自"一次投入、长期复用"，但复用的前提是能被正确触发——所以 description 的精度直接决定沉淀的价值能否兑现。[来源 1]

纯文字兜底：这张流程图描述 Skill 生命周期的四个阶段。① 沉淀：编写 SKILL.md（含 YAML 元数据与正文），是一次性投入；② 加载：靠元数据与用户意图做语义匹配，命中才加载正文，未命中则不加载、不占上下文；③ 复用：按正文描述的流程执行任务，产出落到约定位置；④ 迭代：根据使用反馈修订 SKILL.md，回到阶段①形成版本更新。收益是"写一次、任意会话可用、团队共享、改一处全部生效"；代价是 description 写不准会导致触发失败，写太宽会导致误触发。

3.3 Skill 与上下文、Agent 的交界

  • 与上下文交界：Skill 的元数据是"常驻的极小成本"，正文是"按需的较大成本"。它用这个分层换来了"能力可扩展但上下文不爆"。
  • 与 Agent 交界：Skill 只告诉 Agent"怎么做"，不替它决定"做不做"。是否加载、是否遵循，仍由 Agent 在循环中判断——这也是为什么 Skill 不能当强制约束用。

4 · 三者协作（一张表）

维度大模型的上下文AgentSkill
本质舞台（每次推理的输入边界）在舞台上跑循环的程序交给程序的工作手册
生命周期一次性（每次推理重新拼装）运行时（循环持续到终止）持久（文件形式，跨会话）
容量约束受窗口上限约束受最大轮次与成本约束理论上不限（按需加载）
解决的问题"能看见什么""决定做什么""按什么流程做"
主要操作填装、压缩、检索推理、调用、观察加载、引用、迭代
典型失效信号中段信息被忽略、请求超窗无限循环、错误累积放大description 模糊导致不触发

一句话串起来

Skill（把经验沉淀成文件）→ 被触发后加载进上下文（短期舞台）→ Agent 基于上下文自主决策、调用工具 → 工具结果回填上下文 → 决定下一步 → 直到终止；过程中产生的稳定结论又可沉淀回文件，形成下一轮的 Skill 迭代。

把这三者当一个整体看：Skill 写"怎么做"，上下文决定"能看见什么"，Agent 负责"决定做什么"。三者配合得好，AI 应用就稳定；任意一环失衡，问题就会从那一环暴露出来。
