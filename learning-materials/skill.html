Skill（技能）

AIskillprogressive-disclosurecapability-extension
生成日期：2026-09-12 · 视角：AI Agent 工程 / 自我学习者 · 格式：HTML
一句话定义：Skill 是一份打包好的"领域工作手册"——由包含 name 与 description 的 YAML 元数据、一份说明工作流的 SKILL.md、以及按需加载的辅助资源（参考文档、脚本、素材）组成。它的核心设计是渐进式披露（progressive disclosure）：默认只加载极小的元数据，用到哪一层才加载哪一层。[来源 1][来源 2]
假设标注：本资料假设读者了解 Agent 与上下文的基本概念（可先读本目录的 agent.html 与 llm-context.html），但未自己写过 Skill。文中的"Skill"特指 Anthropic Agent Skills 这一体系下的概念。

1 · 学习目标

学完这份资料后，你应该能够：

  1. 说清 Skill 由哪三部分组成，以及"渐进式披露"到底在解决什么问题。
  2. 把 Skill 与 System Prompt、Tool、RAG 放在一起比较，说明各自负责什么。
  3. 为一个自己熟悉的工作流写出 Skill 的 description，并能判断它是否足够可触发。

2 · 核心问题

  1. Skill 的 YAML 元数据为什么必须写得足够具体？触发失败会有什么后果？
  2. 为什么装了很多 Skill 也不会把上下文撑爆？代价是什么？
  3. Skill 和 System Prompt 都可以"写指令"，什么时候该用哪个？
  4. 纯文档型 Skill（不带任何脚本）是有效的吗？

3 · 个人解释

🔍 本板块含个人理解，标注为「待人工复核」的部分建议用自己的话再改写一遍。

我以前把 Skill 当成"更长的提示词"，看完 Anthropic 的官方说明后才意识到，它真正的创新是"怎么装"而不是"装了什么"。

我的理解是：Skill 像给新同事的一本岗位手册。手册封面写着"市场部 · 入职指南 · 关键词：发邮件、对外沟通、合规"——HR 扫一眼封面就知道该把这本书递给谁。这是第一层：始终可见的元数据。

新同事真正要起草一份对外合同时，才会翻到"合同模板"那一章。这是第二层：按需加载的正文。如果这一章里提到一个合规检查脚本，他会去运行那个脚本，而不是把脚本全文抄进脑子里——这是第三层：用到才调用的资源。

这个三层设计解决了一个我之前没意识到的问题：能力可以装很多，但"注意力"是有限预算。如果每个 Skill 都把全部内容常年塞在上下文里，装到第十个的时候模型就已经看不清重点了。渐进式披露相当于把"详略"交给使用时机决定——平时只占封面那一点位置，需要时才展开。

4 · 核心机制 / 组成

  • 三级加载，节省上下文：第一级是 YAML 元数据（始终加载，体量很小）；第二级是 SKILL.md 正文（在 description 匹配时加载）；第三级是随附资源（在实际用到时按需读取或执行）。[来源 2]
  • YAML frontmatter 是触发器：name 是标识，description 写明"何时该用我"，由模型基于语义匹配决定是否加载——所以描述写模糊，Skill 就会"该上场时不上场"。[来源 1]
  • 可携带三类资源：参考文档用于按需查阅；脚本用于确定性执行（不必把代码读进上下文）；素材用于产出物（模板、字体等），而非加载进上下文。[来源 2]
  • 两级作用域：项目级（仓库内随仓库共享）与用户级（跟随个人跨项目）。作用域决定了"谁知道这个 Skill 存在"。
  • 可组合与可移植：Skill 之间可以叠加使用；同一份 Skill 在不同产品/环境中携带同一套工作流——这是官方强调的两个特性。[来源 1]
  • 触发依赖语义匹配，不是文件系统：Skill 能被用上，前提是它的元数据与用户意图在语义上对得上。因此"能不能被触发"是设计 Skill 的第一等指标。

5 · 可视化讲解

图 1 · Skill 的三级加载机制
1
元数据层 · YAML frontmatter
name + description。始终加载，模型靠它判断"这个 Skill 该不该上场"。
▸ 加载时机：始终  |  体量：极小（约百 token 量级）
2
指令层 · SKILL.md 正文
适用场景、输入字段、生成步骤、输出结构、自检要求等工作流说明。
▸ 加载时机：description 匹配成功后  |  体量：中等（官方建议控制在数千 token 以内）
3
资源层 · 参考文档 / 脚本 / 素材
详细模板、可执行脚本、产出物素材。执行脚本不等于把脚本读进上下文。
▸ 加载时机：实际用到时  |  体量：理论上不设限

图说：装 100 个 Skill，常驻上下文的也主要是第一层那点元数据——详情要等到被触发才展开，这就是"能力可扩展但上下文不爆"的原因。[来源 1][来源 2]

纯文字兜底：这张图展示 Skill 的三级加载结构。第一级是 YAML 元数据（name 与 description），始终加载、体量极小，模型靠它判断是否触发该 Skill；第二级是 SKILL.md 正文，只有在元数据与用户意图匹配成功后才加载，内容是可执行的工作流说明；第三级是随附资源（参考文档、脚本、素材），只有在实际用到时才读取或执行。关键结论：由于默认只有第一级常驻，因此可以同时安装很多个 Skill 而不会挤爆上下文。
图 2 · 四种"扩展 Agent 能力"的机制各管一段
Skill
教 Agent「怎么想 / 按什么流程做」——沉淀工作流与领域规范
Tool
给 Agent「能做什么」——提供可调用的动作与数据接口
RAG
让 Agent「查得到」——运行时按需召回事实性内容
System Prompt
定 Agent「底层约束」——常驻的角色、边界与硬性规则

⚠️ 各条长度为示意，用于表达"分工不同"而非"体量大小"。

图说：这四者不是互相替代的关系——Skill 管流程，Tool 管动作，RAG 管事实，System Prompt 管约束；一个成熟的 Agent 通常四者并用。[来源 1][来源 3]

纯文字兜底：这张对照条说明四种能力扩展机制的分工。Skill 负责"教 Agent 怎么想、按什么流程做"，用来沉淀可复用的工作流与领域规范；Tool 负责"给 Agent 能做什么"，提供可调用的动作与数据接口；RAG 负责"让 Agent 查得到"，在运行时按需召回事实性内容；System Prompt 负责"定 Agent 的底层约束"，常驻角色定位、边界与硬性规则。四者互补而非互斥。（各条长度为示意，表达分工差异而非实际体量。）

6 · 应用场景

谁：本仓库的使用者。
什么环节：想系统学习一个新概念，并留下一份结构统一、来源可查的资料。
解决什么问题：每次都要临时拼提示词，输出结构每次都不一样，参考链接还经常是模型当场编的。

本仓库的 concept-learning-generator Skill 就是为解决这个问题写的。它的结构：

.workbuddy/skills/concept-learning-generator/
└── SKILL.md     # 单文件即可
                 # ├─ YAML: name + description（何时触发）
                 # └─ 正文: 输入字段 / 5 步流程 / 9 个输出板块 /
                 #          资料来源要求 / 自检清单 / 迭代规则

当用户说"用 concept-learning-generator 学习一下 CAP 定理"时，执行路径是：

  1. 模型比对用户意图与 description → 语义匹配成功。
  2. 加载 SKILL.md 正文（第二级）。
  3. 按正文的 5 步流程执行：先检索真实来源，再按 9 个板块组织，撰写第一人称解释，生成独立 HTML，最后过一遍自检清单。
  4. 产出落到 learning-materials/cap-theorem.html，并在索引中追加一行。

整个过程用户只说了一句话。这就是 Skill 的价值：把"我每次都该这么做"的经验，从一次性提示词变成可复用的文件。

7 · 易混淆 / 使用边界

常见误解正解
Skill 就是高级 System Prompt Skill 有触发机制（按 description 按需加载）、可携带资源、有独立作用域；System Prompt 是每次请求都会塞进上下文的固定指令，没有触发选择逻辑。[来源 1][来源 2]
Skill 装得越多，Agent 越强 每个 Skill 的元数据都会占上下文（虽小，但乘以数量）。堆太多会稀释注意力，也会造成触发歧义（多个 Skill 都"看起来像"时更容易选错）。建议按项目需要隔离并定期清理。[来源 1]
Skill 必须配代码才有效 纯文档型 Skill 完全有效——脚本是可选的。Skill 的核心是"领域知识 + 工作流"，不是"代码"。
description 随便写写就行 description 是唯一的触发依据。写得模糊会导致"该上场时不上场"；写得过于宽泛会导致"不该上场时乱上场"。这是 Skill 设计中最该反复打磨的一行字。[来源 1]

不适用 / 会失效的情形：

  • 只用一两次的任务 —— 直接写一次提示词更快，不必为它建 Skill。
  • 需要实时变化的数据 —— Skill 是文件，不承载动态数据；这类需求应交给检索或工具。
  • 需要强制执行的硬约束 —— Skill 是"指导"而非"沙箱"，真正的安全边界要靠权限与工具设计，不能指望 Skill 文本挡住越权操作。
  • 概念极度模糊、流程尚未稳定时 —— 过早固化会把手册写成错误的规范，反而放大问题。

8 · 自测问题

先自己作答，再展开答案对照。

简答题

  1. 【概念辨析】Skill 和 System Prompt 都能"给模型下指令"，二者最本质的区别是什么？
    查看答题要点

    要点：本质区别在"是否按需触发"。System Prompt 是每次请求都必须常驻的固定指令；Skill 的元数据常驻，但正文只在 description 与用户意图语义匹配成功后才加载，且可以携带脚本与文档等资源。因此 Skill 解决的是"能力很多但上下文有限"的规模化问题，System Prompt 解决的是"每次都要遵守的底层约束"。[来源 1][来源 2]

  2. 【核心机制】为什么安装大量 Skill 不会把上下文撑爆？代价又在哪？
    查看答题要点

    要点：因为采用的是渐进式披露——默认只有第一级的元数据常驻，正文与资源都要等触发后才加载。代价是：① 每个 Skill 的元数据仍会累积占用少量上下文；② 数量多了会造成触发歧义，模型可能选错或选不出；③ 元数据本身写不好会导致该触发的没触发。所以"能装很多"不等于"装越多越好"。[来源 1]

选择题

  1. 【风险与边界】你写了一个 Skill，但用户在实际使用中它几乎从不被触发。最可能的原因是？
    A. SKILL.md 正文写得太长
    B. YAML 中的 description 没有写清"什么情况下该用"
    C. 没有给 Skill 配 scripts 目录
    D. 忘记加 agent_created: true
    查看答案与理由

    正确答案：B
    理由：触发判断只依赖元数据，其中 description 是模型判断"何时用我"的唯一依据。正文再精彩，也得先被加载才起作用；scripts 是可选资源，与触发无关；agent_created 影响的是能否被后续维护，不是触发。所以描述模糊是触发失败的首要原因。[来源 1]

应用题

  1. 【具体应用】请为你自己熟悉的一个重复性工作流（如"每周整理数据""写周报""审查代码"）设计一个 Skill 的 description，要求写清：它做什么、什么情况下该触发、什么情况下不该触发。
    查看答题要点

    要点：合格的 description 应包含三要素——① 能力说明（这个 Skill 产出什么）；② 触发语示例（"帮我做 X""整理 Y"这类用户可能真实说出口的话）；③ 排除边界（明确写出不适用的情形，防止误触发）。评分重点在于是否有"排除项"——只写能做什么、不写不做什么的描述，是常见的触发歧义来源。

  2. 【风险与边界】有人说"既然 Skill 能沉淀知识，那我把它当成团队规范文档用，让 Agent 严格遵守里面的所有规则"。这个想法有什么风险？
    查看答题要点

    要点：风险至少三点：① Skill 是指导性文本，不是强制执行机制，模型可能忽略或曲解；② 规则写成冗长清单会降低信噪比，反而削弱执行率（官方建议是给精简、具体、可判定的指令）；③ 真正的硬约束应落在权限、工具设计与校验环节，而不是依赖一段自然语言。答出"Skill 不等于强制约束"这一核心判断即可。
