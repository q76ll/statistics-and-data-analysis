Skill（技能）

AIskillcapability-extensionprompt-engineering
日期：2026-09-05 · 深度：standard · 受众：自我学习者
Skill（在 Anthropic / WorkBuddy 等 Agent 体系下）= 一个打包好的"领域工作手册"：YAML 元数据告诉 Agent 何时加载，主 SKILL.md 告诉它怎么工作，references/ scripts/ assets/ 提供按需加载的辅助资源。它是 Agent 时代"能力分发"的最小单元。

个人理解

我以前总把 Skill 想象成"高级提示词"。后来翻 Anthropic 的 Introducing Agent Skills 那篇发布博客才意识到——Skill 真正的创新不是"内容更复杂"，而是"渐进式披露 (progressive disclosure)"。

用一个比喻：你给一个新同事一份岗位手册。手册封面写着"市场部 · 入职指南 · 关键词：发邮件、Slack、合规"，HR 一眼就知道该把这本手册递给谁。这是 Level 1：始终加载的元数据。

新人拿到手册翻开第一页，只有当 TA 真正要去干相关活儿（比如要起草一份对外合同）时，才会翻到"合同模板"那一章。这是 Level 2：按需加载的指令主体（SKILL.md）。

如果合同模板里引到一个"对外合规检查脚本"，TA 才会去执行那个脚本——脚本本身不加载到脑子里。这是 Level 3：资源（脚本/参考文档/素材）。

这个三层加载的好处是：你可以装 100 个 Skill 而 Agent 不会爆炸——它的"脑子（context window）"里始终只有 ~100 token/个 的元数据，详情来了再说。这就是"能力分发"的最小单元：一次制作，长期复用，按需加载。

核心机制

  • 三级加载，节省上下文。Level 1 (YAML frontmatter, ~100 token) 始终加载；Level 2 (SKILL.md body, ≤5k token) 在 description 触发时加载；Level 3 (references / scripts / assets) 在用到时按需加载或执行。
  • YAML frontmatter 是触发器。name 是 ID，description 写明"何时用"，由模型基于语义匹配判断是否触发。
  • 可携带三类资源：scripts/ 是可执行代码（deterministic、节约 token）；references/ 是按需查阅的文档；assets/ 是素材（模板、字体、图表等）——用于输出而非加载到上下文。
  • 两层作用域：项目级（仓库 .workbuddy/skills/<name>/，随仓库共享） vs 用户级（~/.workbuddy/skills/<name>/，跟随你个人跨项目）。
  • 渐进式披露设计哲学。能装很多个 Skill 而不爆上下文——因为默认只加载元数据，详情按需。
  • 可被 SkillManage 维护。agent_created: true 标记的 Skill 可被 SkillManage 工具修改/删除；marketplace 安装的默认只读。

一个具体的应用场景

本仓库的 concept-study Skill 就是一个具体例子。它的目录结构：

.workbuddy/skills/concept-study/
└── SKILL.md          # 主入口
                           # 工作流：输入概念 → 个人理解 → 核心机制 →
                           # 应用场景 → 混淆边界 → 自检 → 参考资料
                           # 输出路径：learning-materials/<slug>.html
                           # 自检清单：8 条交付前必须打勾

用户说"用 concept-study 学习贝叶斯定理"，Agent 的执行路径：

  1. 比对用户意图与 concept-study 的 description → 匹配。
  2. 读取 SKILL.md（Level 2 加载）。
  3. 按 SKILL.md 的步骤：先消歧（贝叶斯定理 vs 朴素贝叶斯）→ 写个人理解 → 拆机制 → 找例子 → 列混淆 → 出题 → 找资料。
  4. 写到 learning-materials/bayes-theorem.html，并在 index.html 追加一行。

如果以后有一个 data-viz Skill（专门教可视化），它和 concept-study 可以并存——description 决定谁上场，不会互相污染上下文。

混淆与边界

  • 误解：Skill = 高级 system prompt。 正解：Skill 有触发机制（按 description 加载）、可携带资源、有自己的作用域。System prompt 是一次性手工塞进上下文的"指令"，没有触发选择逻辑。
  • 误解：Skill 越多 Agent 越强。 正解：每个 Skill 的 YAML 都会占上下文（虽然小，但 ~100 token × N）。过度堆 Skill 会稀释注意力。建议按需启用 + 项目级隔离。
  • 误解：Skill 必须配代码。 正解：纯文档型 Skill（像本仓库的 concept-study）完全有效；scripts/ 是可选的。Skill 的核心是"领域知识 + 工作流"，不是"代码"。
  • 误解：Skill 是模型厂商黑话。 正解：是通用范式——Anthropic、OpenAI、各类 Agent 框架都有类似机制，叫法略有差异（Skill / Custom Instructions / Plugin / Tool Manifest）。

自检问题

  1. 【复述】用自己的话讲清楚 Skill 是什么、它和 System Prompt 差在哪？
  2. 【对比】Skill、Tool、MCP、RAG 在"扩展 Agent 能力"这件事上各自解决什么问题？
  3. 【应用】你现在学的"统计与数据分析"课，能写出一个什么样的 Skill？请用一句话写它的 description。
  4. 【判断】什么场景不该用 Skill（直接 system prompt 就行）？什么场景必须用 Skill？
  5. 【延伸】Skill 的"项目级 / 用户级"两层结构是为了解决什么问题？想想"团队新人入职"这个场景。
