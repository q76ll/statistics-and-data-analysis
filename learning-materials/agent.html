Agent（智能体）

AIagentautonomytool-use
日期：2026-09-05 · 深度：standard · 受众：自我学习者
LLM Agent = 由大模型驱动、能自主循环地读信息 → 做决策 → 调用工具 → 看结果 → 再决策，直到完成目标或触发终止的程序。它和普通聊天机器人的核心差别不在"会不会调工具"，而在"下一步要不要再调、调用什么"由谁来决定——答案是 Agent 自己。

个人理解

我自己在理解 Agent 时，最容易把它和"Chatbot + 一些插件"混淆。后来我是这样把 Agent "看穿"的：

把它想成一个会自己拉清单的助手。用户说一句"帮我调研 GitHub 上最近 30 天最热的 5 个 AI Agent 仓库"，Agent 不会立刻返回一个答案——它会先在脑子里（其实在 system prompt + 任务描述里）拆出步骤：先搜索、再筛选、再读 README、再抽取要点、再写报告。每一步它都会停下来看结果，决定"够不够？要不要再来一次？"。

这就是 Anthropic 团队在工程博客里反复强调的"agent loop"——一个非常朴素的循环：

while not done:
    plan   = LLM(think_with_tools, current_state)
    action = tool.execute(plan.next_step)
    state  = state.update(action.result)
    if state.satisfies_goal(): done = true

这段伪代码看着简单，但 Anthropic 自己说过："most successful implementations weren't using complex frameworks or specialized libraries. Instead, they were building with simple, composable patterns."——厉害的 Agent 实现不是花哨框架，是这层朴素循环的仔细打磨。真正的难点在工具接口设计（tool ergonomics）和错误恢复，而不是 loop 本身。

核心机制

  • 由 LLM 拥有决策权：下一步做什么（调哪个工具、用什么参数、何时停）由 LLM 在循环里动态决定，不是写死代码编排。
  • 闭环循环：感知（读系统/工具返回）→ 决策（LLM 推理）→ 行动（调工具）→ 观察（读结果）→ 再决策——这是一个不断自我修正的反馈环。
  • 可调用工具：搜索、读文件、运行代码、发请求……这些工具是 Agent 的"手脚"。没有工具的 Agent 只是一个普通聊天机器人。
  • 短期状态全装在上下文里：每一次循环 LLM 看到的输入（系统提示 + 历史消息 + 工具返回）就是 Agent 的全部短期记忆。上下文窗口爆了 = Agent 失忆。
  • 必须有终止条件：要么任务完成，要么达到最大步数，要么置信度太低主动停下。无限循环会一直烧钱。
  • 错误会累积：每一步若有偏差，偏差会沿着循环放大；所以生产环境的 Agent 必须有 guardrails（人审节点、沙盒、超时、回滚）。

一个具体的应用场景

场景：你让 Agent "把本仓库 README 和 CHANGELOG 翻译成英文，PR 到 main 分支"。Agent loop 跑起来是这样：

  1. 先用 read_file 读 README.md 和 CHANGELOG.md，观察内容长度（>10k token 时可能要分块）。
  2. 把"翻译目标 + 当前任务状态"塞进 LLM，让它列一个清单（拆 job）。
  3. 对每个文件，循环：用 translate_chunk 翻译一段 → 用 write_file 写回 → 检查是否完整 → 进入下一段。
  4. 遇到低级错误（如语法错误未通过 lint），回到循环开头自己修一次；超过两次就停下来把这段加入 NEEDS_HUMAN_REVIEW 列表。
  5. 全部完成后调用 git_add_commit_push，并把 PR URL 报告给用户。

整个过程用户只需要说一句话、最后收一个 URL。这件事如果用 Chatbot 实现，user 会写一段 200 字的 prompt 让 Chatbot 教 自己做一遍——区别在于谁负责中间那十几步。

混淆与边界

  • 误解：Agent = Chatbot + 几个工具。 正解：关键是循环。Chatbot 不会"决定下一步要不要再调工具"；Agent 会。
  • 误解：Agent 越"聪明"越好。 正解：Anthropic 的明确建议是"find the simplest solution possible, and only increase complexity when needed"——能写死 pipeline 的任务不要硬上 Agent，烧钱、慢、还会出怪错。
  • 误解：长上下文窗口 = Agent 不会失忆。 正解：上下文窗口再大也不解决"哪些 token 才是当前最相关"——这靠 Skill、压缩、检索（RAG）等"上下文工程"解决，不是单靠窗口大。
  • 误解：自主 Agent 没有 SOP 需求。 正解：Anthropic 在多 Agent 研究博客里特别指出："Setting explicit guardrails to prevent the agents from spiraling out of control."——人审节点、终止条件、回滚剧本一样都不能少。

自检问题

  1. 【复述】用自己的话讲清楚 Agent 是什么、它和普通 Chatbot 差在哪一步？
  2. 【对比】Agent 和 Copilot、Workflow（固定管线）关键差别是什么？给出"该用 Agent 但不该用 Copilot"的一个场景。
  3. 【应用】你最近做的一个任务里哪一步最像 agent loop？请用 感知→决策→行动→观察 描述一遍。
  4. 【判断】什么样的任务不该升级成 Agent？（提示：可枚举、固定流程、几乎不出错的）
  5. 【延伸】Agent loop 跑到第 N 步，上下文已经装满了——你猜会有哪些常见解法？各自代价是什么？
