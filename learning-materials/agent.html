Agent（智能体）

生成日期：2026-09-12 · 视角：AI Agent 工程 / 自我学习者 · 格式：HTML
一句话定义：Agent 是由大模型驱动、能在循环中自主使用工具直到完成目标（或触发终止条件）的程序。它与普通 Chatbot 的差别不在"会不会调工具"，而在下一步调不调、调什么，由模型自己决定。[来源 1]

3 · 个人解释

🔍 本板块含个人理解，标注为「待人工复核」的部分建议用自己的话再改写一遍。

我一开始把 Agent 理解成"Chatbot + 一堆插件"，后来发现这个理解漏掉了最关键的一环。

我现在的理解是：Agent 像一个会自己拉清单的助手。你说"帮我查一下最近 30 天 GitHub 上最热的 5 个 AI Agent 仓库"——它不会直接给答案，而是先在脑子里拆步骤：先搜、再筛、再读 README、再抽取要点、再写报告。每做完一步，它会停下来看一眼结果，然后自己决定"够了没有？要不要再来一轮？"

它和普通 Chatbot 最大的不同是：Chatbot 由人写死下一步做什么；Agent 由模型自己决定下一步做什么。这个差别看起来很小，但它意味着程序的控制流从"编译器决定"变成了"模型决定"——这既是 Agent 强大的原因，也是它不可控、烧钱、会跑偏的原因。

我用一个比喻记住它的本质：普通程序像一张写死的菜谱，第几步放盐都是定好的；Agent 像一个会看锅里情况随时调整的厨师——菜谱只是参考，真正决定下一步的是他对当前锅里的观察。代价是：这位厨师可能自由发挥过头，把菜做糊了。

4 · 核心机制 / 组成

  • 由 LLM 掌握决策权：调哪个工具、用什么参数、什么时候停，由 LLM 在循环中动态决定，而不是写死在代码里。[来源 1]
  • 闭环循环（agent loop）：感知（读工具返回）→ 决策（LLM 推理）→ 行动（调工具）→ 观察（读结果）→ 再决策。这是一个不断自我修正的反馈环。
  • 工具是手脚：搜索、读写文件、执行代码、发请求。没有工具的 Agent 只是一个普通 Chatbot。工具设计要"token 高效、功能不重叠、错误可恢复"。[来源 1]
  • 短期状态全在上下文里：每轮循环 LLM 看到的输入（系统提示 + 历史消息 + 工具返回）就是 Agent 的全部短期记忆。上下文爆了 = Agent 失忆。
  • 必须有终止条件：任务完成、达到最大步数、或置信度过低主动停下。无限循环会持续烧钱。
  • 错误会沿循环放大：单步偏差会被后续步骤继承并放大，因此生产环境必须有 guardrails（人审节点、沙盒、超时、回滚）。[来源 2]

图说：Agent 与普通程序的分水岭就在"决策"这一格——它由 LLM 完成而非代码写死，因此每一轮都可能走向不同的下一步。

纯文字兜底：这是一个四步闭环——① 感知：Agent 读入当前工具返回或用户输入；② 决策：LLM 判断下一步该做什么；③ 行动：调用某个工具；④ 观察：读取工具结果并更新状态。之后结果回填进上下文，重新从①开始。循环在两个条件下终止：任务完成，或触发终止条件（如达到最大步数）。

图说：上下文不是无限资源——每轮循环都会往窗口里追加内容，三轮之后注意力开始被稀释，接近上限时必须主动整理。[来源 3][来源 4]

纯文字兜底：这张图展示"循环轮次越多，上下文占用越高"的趋势（数值为示意）。第 1 轮只有系统提示和用户问题；第 3 轮加上了工具定义和前两轮返回；第 6 轮多轮工具输出累积，模型对中段细节的注意力开始被稀释；第 10 轮接近窗口上限，必须采取压缩、截断或丢弃低价值内容的措施。核心结论：上下文占用随循环单调增长，不会自动回落。

6 · 应用场景

谁：一个需要维护文档的工程师。
什么环节：把仓库里两份中文文档翻译成英文并提 PR。
解决什么问题：免去手工逐段翻译 + 复制粘贴 + 提交的十几步重复劳动。

具体跑起来是这样：

  1. 用 read_file 读 README.md 和 CHANGELOG.md，观察内容长度（超过一定 token 就要分块）。
  2. 把"翻译目标 + 当前状态"交给 LLM，让它列一个任务清单。
  3. 循环处理每个文件的每一段：翻译 → 写回 → 检查完整性 → 进入下一段。
  4. 遇到 lint 失败等问题，回到循环开头自行修复一次；连续两次失败就停下来，把这段加入 NEEDS_HUMAN_REVIEW 列表。
  5. 全部完成后调用提交工具，把 PR 链接报告给用户。

整个过程用户只说一句话、最后收一个链接。中间那十几步的"决定与重试"由 Agent 承担——这就是它和 Chatbot 的实际差别。

7 · 易混淆 / 使用边界

常见误解正解
Agent = Chatbot + 几个工具 关键是循环。Chatbot 不会自己决定"下一步要不要再调工具"；Agent 会。[来源 1]
Agent 越自主越好 Anthropic 明确建议："find the simplest solution possible, and only increase complexity when needed"。能用固定 pipeline 解决的任务不要硬上 Agent——更烧钱、更慢、还会出怪错。[来源 1]
长上下文窗口 = Agent 不会失忆 窗口再大也解决不了"哪些 token 才是当前最相关"。这要靠上下文工程（压缩 / 检索 / 结构化笔记）解决。[来源 3][来源 4]
自主 Agent 不需要 SOP Anthropic 在多 Agent 研究博客中特别指出要 "Setting explicit guardrails to prevent the agents from spiraling out of control." 人审节点、终止条件、回滚剧本一个都不能少。[来源 2]

不适用 / 会失效的情形：

  • 任务高度可枚举、流程固定、几乎不出错 —— 写死的 workflow 更快、更便宜、更可测。
  • 对延迟极度敏感 —— 多轮循环的累积延迟通常远高于单次推理。
  • 错误不可逆的场景（如生产数据库写操作） —— 除非有沙盒与人工确认节点，否则不应交给自主 Agent。

8 · 自测问题

先自己作答，再展开答案对照。

简答题

  1. 【概念辨析】用你自己的话说明 Agent 和 Workflow（固定管线）的核心差别是什么？
    查看答题要点

    要点：控制流的归属不同。Workflow 的步骤由开发者预先写死（如 prompt chaining、routing），每一步走哪儿是确定的；Agent 的下一步由 LLM 在运行时动态决策。因此 Workflow 可预测、好测试、成本可控，Agent 灵活、能处理未预期分支，但更贵、更难测、行为有不确定性。[来源 1]

  2. 【核心机制】agent loop 有哪四个环节？其中哪个环节一旦缺失，Agent 就退化成普通 Chatbot？
    查看答题要点

    要点：感知 → 决策 → 行动 → 观察。缺"决策"（即由模型自主决定下一步）时，程序就变成按固定顺序调工具的 Chatbot/Workflow。缺"观察"则无法根据结果修正，退化为一次性调用。

选择题

  1. 【风险与边界】以下哪种任务最不适合升级为自主 Agent？
    A. 从多个数据源汇总信息并写一份报告
    B. 代码库的大范围重构，需要反复试错
    C. 每天凌晨把固定的三个 CSV 按固定规则合并成一张表
    D. 排查一个原因未知的线上问题
    查看答案与理由

    正确答案：C
    理由：该任务流程完全固定、输入输出可枚举、几乎不会出现需要动态决策的分支——写死的脚本更快、更省钱、更容易测试。A/B/D 都存在"路径不确定、需要根据中间结果调整"的特征，是 Agent 的合理用武之地。[来源 1]

应用题

  1. 【具体应用】回忆你最近做过的一个多步骤任务（如整理资料、写报告、改代码），用"感知 → 决策 → 行动 → 观察"把它描述一遍，并指出哪一步最适合交给 Agent、哪一步必须由人把关。
    查看答题要点

    要点：应能一一对应四个环节，并给出理由。通常"行动"和"决策"适合交给 Agent（信息收集、草拟、批量改写），而"观察"之后的最终判断、涉及不可逆操作（提交、发布、删除）的环节必须保留人工确认节点。评分看是否说清了"为什么这一步可以/不可以放手"，而不是环节划分是否完美。

  2. 【风险与边界】某 Agent 需要跑 30 轮工具调用才能完成一个任务，跑到第 20 轮时开始出现前后矛盾。请给出至少两种可能的原因和对应的缓解措施。
    查看答题要点

    要点：可能原因包括——① 上下文接近/超过窗口，早期关键信息被挤出或被稀释（lost in the middle），缓解：压缩历史、结构化笔记、把关键状态写入外部文件；② 早期某一步的错误被后续步骤继承放大，缓解：设置检查点、在关键步骤后做校验、必要时回滚重跑；③ 工具返回内容过多挤占注意力，缓解：精简工具输出、只保留高信号字段。答出任意两点并给出对应措施即可。
