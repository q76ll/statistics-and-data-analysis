# 大模型的上下文 (Context)

## 一句话定义

大模型的**上下文 (context)** = 一次推理中，模型能"看见"并据以生成下一段文本的**全部输入**；它通常被切分成 **tokens**，总长度受 **context window (上下文窗口)** 限制。

## 为什么学它

- 上下文窗口大小直接决定模型一次能"装下"多少资料——多轮对话、长文档分析、Agent 工具回执，全挤在同一个盒子里。
- 大多数 LLM 应用 bug 不是模型笨，是**上下文装错了东西**（塞太多 / 塞太少 / 塞无关 / 塞敏感信息）。

## 关键特征（5 条）

- **以 token 计，不以字符计**。中文字符 ≈ 1–1.8 token；英文单词 ≈ 1.3 token。token 是模型的最小"感知单位"。
- **有上界**。当前主流模型 8k–200k token 不等；超出窗口会被截断或报错。
- **线性计费**。输入 + 输出 token 数决定费用（输入便宜，输出更贵）。
- **注意力随距离衰减**（趋势）。窗口越大，每个 token 分到的注意力越稀——**窗口大 ≠ 记得全**（"lost in the middle" 现象）。
- **可被显式塑造**。system prompt、消息摘要、检索增强 (RAG)、工具回裁剪，都属于"上下文工程"。

## 与相近概念的对比

| 概念 | 谁拥有 | 是否持久 | 典型大小 |
|---|---|---|---|
| **Context Window** | 一次推理的输入 | 否（临时） | 8k–200k tokens |
| Conversation History | 多轮对话累积 | 视设计而定 | 通常受限于 Context Window |
| System Prompt | 模型启动时的固定前置 | 是（每次会话加载） | 几百–几千 tokens |
| Long-term Memory | 跨会话存 | 是（外部） | 任意，按需塞入 Context |
| Embedding / RAG 召回 | 检索时的 top-k 片段 | 是（向量库） | 受召回数量限制 |

> 一句话区分：**上下文是模型这次推理"看见的所有 token"——它不是记忆，是"舞台"**。

## 一个具体的例子

> 场景：让模型总结一份 50 页 PDF（约 3 万 tokens）。
> 直接塞 → 模型能读到，但对中后段细节的引用显著下降（"迷失中间"）。
> 改进：切成 1k-token 的 chunks，每段先做摘要，再把所有摘要塞入上下文让模型作答——**塞进去的 token 变了，但效果可能更好**。
> 启示：扩大窗口是下策，**管好塞什么**才是上策。

## 常见误解（3 条）

- **误解：上下文窗口 100k = 模型能精确用满 100k。** 正解：超长上下文中模型对中后段细节的引用显著下降。
- **误解：清空对话 = 模型失忆。** 正解：清空只清掉**当前会话的上下文**；真正的"记忆"看你如何设计 system prompt + 外部存储。
- **误解：提示词 (prompt) ≠ 上下文。** 正解：提示词是上下文**的一部分**；上下文还含历史消息、工具返回、system 指令等所有输入。

## 自检问题

1. 【复述】一句话讲清"context window"和"对话历史"的区别？
2. 【对比】Long Context 和 RAG 都试图"让模型看到更多资料"，它们各自的核心代价是什么？
3. 【应用】你刚做的一次任务里，输入的 token 大概有多少？哪段最占空间？能不能砍？
4. 【判断】什么时候应该**压缩上下文**（摘要/截断），什么时候应该**扩大窗口**？
5. 【延伸】如果是 Agent，它的"上下文"和"长期记忆"是怎么分界的？
